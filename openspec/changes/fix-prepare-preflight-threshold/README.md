# fix-prepare-preflight-threshold

**状态：2026-11-08 提案，等待项目所有者确认后实现。未获确认前不写实现代码。**

## 问题（本机实测）

当前构建在**全新数据根（新用户首次安装）**上安装 Qwen-Image 2.1 Turbo 时，安装器在量化前报：

> 可用内存不足，未开始构建 Qwen/MOSS 量化缓存（未激活任何安装文件）。当前可用物理内存 22.6 GiB（要求 ≥28 GiB）或可用提交余量 24.8 GiB（要求 ≥26 GiB）……

同一台机器 2026-11-04 曾成功安装同一批模型（`C:\ist-a` 的 Qwen base/Turbo、MOSS 均有 prepared 缓存），当时的准备日志显示：

- prepare 进程 commit 峰值实测 **23.003 GiB**（MOSS text encoder），可用物理内存最低 1.147 GiB（靠分页完成）；
- 当次预检 commit 余量 **27.06 GiB**，以 26 GiB 门槛通过（余量的余量仅 1.06 GiB）。

今天重启后 Windows 自动管理的页面文件回到 4.8 GiB，commit 余量为 24.4–24.8 GiB：它**高于实测需要的 23.0 GiB**，却被 26 GiB 门槛拒绝。也就是说：这台 32 GiB 机器**本来能完成量化**，是预检阈值过严把全新安装挡在门外；要求用户调大虚拟内存来迁就软件是不合理的。

## 修复方向

1. 把 commit 余量门槛从 **26 GiB 降到 24 GiB**（= 实测最坏值 23.0 GiB + 1 GiB 安全余量）；保留"可用物理内存 ≥28 GiB"作为另一条通过条件。
2. 当 **prepared 缓存可复用**（模型清单摘要与完整 inventory 摘要匹配）时**跳过内存预检与重新量化**；升级后重装不需要再次量化，不应被内存门槛拦住。
3. 更新失败文案中的门槛数字，保持可行动。
4. 把主规格 `model-installation` 的预检条款同步改为实测口径，并记录"旧 26 GiB 门槛会误拒该机"的证据。

## 为什么不是"让用户调虚拟内存"

- 2026-11-04 同机同模型成功安装，说明 prepare 在本机可行；用户没有改过虚拟内存也能装。
- 预检应阻止"确实无法完成"的机器，而不是要求用户先改系统设置；这是软件回归。
- 另一种"直接放行、失败再报错"的方案风险更大：不能在 16 GiB 机器上把页面文件打爆；因此本轮只修正阈值与复用短路，保持行为可界定。

## 验证方式

- 单元测试：门槛边界（23.99 GiB 拒绝 / 24.00 GiB 通过）、可复用缓存跳过预检。
- 本机全新根实测：修复前 blocked（已有证据）；修复后 Qwen-Image 2.1 Turbo、Qwen-Image 2.1、MOSS 首次安装通过并各完成一次标准档生成。
- 回归：8 GB 参考机口径（commit 余量 60+ GiB）仍通过；低于新门槛的机器仍在量化前得到可行动错误。

## 不做

- 不改分片流式量化（`stream-prepare-low-memory`，所有者已决定暂缓）。
- 不改生成路径、档位或显存预算。
- 不删除或重建用户已有 prepared 缓存。

## 影响

- 代码：`apps/desktop/src/adapters/installation.rs` 的预检常量与调用顺序（先判断缓存可复用再决定是否预检）、错误文案、单元测试。
- 规格：`openspec/specs/model-installation/spec.md` 的"安装期量化准备使用低内存分片路径"要求（阈值与复用场景）。
- 证据：新增 `verification/windows-12gb-standard-tier/S3b-...`（修复后安装与生成）、更新 S3 记录。
- 文档：`doc/15-windows-8gb-tier.md` 不涉及（8 GB 机不受影响）。
