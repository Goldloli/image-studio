# Design

## Context

当前主分支在 `v0.1.1` 之后的主要差异集中在 React 工作区、SQLite v6、会话/作品管理和 Windows 登记文件删除逻辑。现有 Windows 12 GB 标准档认证曾覆盖七个型号、八项能力及真实生成，但当前 GitHub CI 明确不下载模型、不运行 GPU 推理，也不安装和操作原生 GUI。

本 change 不修改产品行为，只调整 Windows 验收的分类与证据口径：当前构建仍必须在 Windows 实机验证功能性风险；只有执行面变化时才重复耗时的模型认证。

## Goals / Non-Goals

**目标**

- 用真实 Windows 安装包验证当前 UI 删除、v6 数据迁移和本地文件管理。
- 复用未受本次差异影响的完整生图认证，不重复下载模型或生成图片。
- 给出确定、可审计的“是否需要生图重认证”判断规则。
- 让功能回归、生图认证和 CI 构建结果使用不同标签，避免互相冒充。

**非目标**

- 不改变生图能力、模型配方、运行时、协议、数据库、安装器或发布流程。
- 不建立持续运行的 Windows GPU CI。
- 不执行模型下载、安装期量化、推理、编辑、去背景、放大或新图片质量检查。
- 不覆盖新的 Windows 版本、显卡架构、显存档位或性能承诺。
- 不把功能回归结果表述为“当前主分支七模型八能力已重新认证”。

## Decisions

### 1. 两种独立验收档

| 验收档 | 当前构建 | 模型推理 | 新图片 | 主要目的 |
| --- | --- | --- | --- | --- |
| Windows 功能回归 | 必须 | 禁止 | 禁止 | 安装、升级、原生 UI、数据与文件管理 |
| Windows 生图认证 | 按触发条件 | 必须 | 必须 | 模型执行、资源、质量、取消/恢复与硬件档位 |

功能回归不因模型已安装而自动发送请求，也不以“页面看起来可用”代替生图认证。报告必须显式写明本次执行的是哪一种档位。

### 2. 功能回归的固定边界

功能回归 SHALL 使用当前 CI 构建的 Windows x64 安装包，在隔离数据根或可丢弃的数据副本中验证：

- 安装、启动、覆盖当前用户数据时的 schema 升级和重启恢复。
- WebView2 原生界面、窗口尺寸、DPI、主题、键盘、中文 IME 与草稿保存。
- 单层导航、保留页面、已删除页面不可达。
- 会话新建、切换、重命名、删除、后继选择和作品来源墓碑。
- 既有作品的查询、筛选、收藏、预览、导出、引用说明、受控删除与重启恢复。
- Windows 只读文件、文件句柄占用、删除未完成/重试和日志。
- 设置、存储路径、启动失败诊断、模型状态只读投影和关于/许可入口。

功能回归 MAY 使用既有正式作品、旧库副本、外部测试图片和界面截图。所有截图只作为操作证据，不属于模型生成输出。

### 3. 执行面变化分类

下列任一路径发生行为变化，视为执行面变化：

- `tools/*worker*`、`tools/inference-supervisor`、`tools/diagnostic-worker`；
- Windows 模型/运行时/worker 清单、固定版本、哈希、依赖锁和量化准备；
- `crates/studio-core` 的请求、计划、配方、设备门槛与执行状态；
- `crates/worker-protocol` 的握手、载荷、候选或执行身份；
- `apps/desktop` 的生成启动、安装器、设备探测、运行时选择和受管进程回收；
- 会改变发送提交、任务冻结、取消/重试或候选正式化语义的接口变化。

纯文档、样式、导航、本地作品管理、不影响执行输入的查询或状态投影通常不构成执行面变化。分类不能仅看目录名；最终以实际 diff 是否改变上述行为为准。

### 4. 生图认证的复用条件

功能回归可复用既有生图认证，仅当以下条件同时成立：

1. 存在完整、可定位且属于目标 Windows 机器的历史认证记录；
2. 当前构建与历史认证基线之间的 diff 审查未发现执行面变化；
3. 当前构建仍能显示既有模型/设备身份、查看和导出既有作品；
4. 报告明确引用历史基线提交、证据路径和本次当前构建提交。

任一条件不成立时，功能回归仍可执行，但不得据此关闭 Windows 生图认证；必须运行已有的完整目标机认证。

### 5. 与 CI 的分工

当前 HEAD 的 GitHub quality/build MUST 先行通过，用于证明编译、单测、Tauri 权限清单、安装包构建与哈希。Windows 功能回归只在 CI 产物基础上验证 CI 无法覆盖的原生界面和文件系统行为；CI 通过不得替代功能回归，功能回归也不得反向补充 CI 未运行的证据。

### 6. 状态与证据

每个测试项使用 `pass | fail | blocked | not_run`。测试记录至少包含：

- 当前提交、安装包 SHA-256、Windows/WebView2 版本和目标数据根；
- 功能回归机器身份；
- 历史生图基线提交、证据路径和执行面 diff 结论；
- 每项截图、DB 查询、文件哈希或命令输出；
- 失败项的可复现步骤、原因和后续 Beads；
- 明确排除项，尤其是模型下载、推理和资源性能。

## Risks / Trade-offs

- **影响面误判导致遗漏执行回归**：分类采用失败关闭原则；任何争议或无法证明的差异都触发完整生图认证。
- **UI 删改破坏发送入口**：功能回归检查入口、参数、草稿和禁用状态，但不发送；发送执行语义仍由现有自动化与历史认证承担。
- **功能验收被误读成模型认证**：报告标题、结论和版本说明必须使用“功能回归”，不得使用“七模型八能力重新认证”。
- **数据迁移或删除误伤用户作品**：只使用隔离根或复制库；文件被占用、只读和中断恢复均使用测试资产。

## Migration Plan

1. 用户确认本 change 后，建立或更新执行用 Beads，并冻结当前提交与 CI 安装包。
2. 完成执行面 diff 审查，确定本次是功能回归，还是功能回归加完整生图认证。
3. 在 Windows 目标机执行 [test-plan.md](test-plan.md)，保存逐项证据。
4. 记录结果、关闭完成的 Beads、归档 change 并合并 `windows-desktop` delta。
5. 若出现执行面变化，另按既有完整 Windows 生图认证流程执行；不得把本 change 的状态延伸为生图通过。
