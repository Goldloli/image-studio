## 3. 上游本机基线

基线使用同一固定 MFLUX、同一模型 revision、q8、尺寸、模板、种子与采样配置，在受控隔离环境直接调用该后端的公开 API/CLI。基线入口和版本完整保存，先完成无网络依赖闭包验证。该基线是集成参考，不能冒称官方 CUDA 环境或未量化高精度结果。

| ID | 级别 | 对象与输入 | 通过条件 |
|---|---|---|---|
| B01 | P0 | Qwen 基础版的 T01–T03 | 三个固定输入真实出图，保存原始样图/参数/耗时和加载信息；本地路径能完成生成 |
| B02 | P0 | Turbo 的 T01–T03 | 真正使用 Turbo 权重/model_config 和固定曲线；8 个去噪步，不能仅给基础版减步数 |
| B03 | P0 | MOSS-SFT 的 T01–T03 及 T04 | 保留 chat template、CFG/skip；JSON 输入不被前置增强或自动改写，保存实际输出 |
| B04 | P0 | 三个配方的离线组件审计 | 整进程树禁网时不访问 HF/补配置/远程自定义代码；失败则回到组件准备，不跳过 |
| B05 | P1 | 基础版与 Turbo、q8 与更高精度的质量探索 | 配方分别标识，仅作研究；不从单图推导优劣或混入同配方集成判定 |

T01–T03 定义如下，每个基线与正式产品执行使用相同输入文件摘要：

| 输入 ID | 完整提示词 | 种子 | 人工检查点 |
|---|---|---:|---|
| T01 | 一只橙色的小猫坐在窗边，窗外是秋天的树叶，温暖自然光，细腻的水彩插画。 | 42 | 主体/窗/秋叶关系、风格、完整图像 |
| T02 | A white ceramic teapot and a blue cup on a wooden table, soft morning light, clean product photography, plain warm background. | 43 | 两个物体、颜色、构图、英文输入 |
| T03 | 一张简洁的咖啡店海报，标题文字必须是“秋日咖啡”，副标题是“周末限定”，米色背景，中间一杯热咖啡，清晰的中文排版。 | 44 | 逐字抄录实际文字，记录错字/缺字和布局；不换种子挑图 |

T04 为 MOSS 官方固定文档所使用 schema 的短 JSON 布局案例，定义目标为标题“周末市集”、副标题“OPEN”、左右分区两个物体。实施准备阶段取得该 schema 的真实字段/坐标约定，生成一份本项目原创的有效 JSON 输入并保存全文、来源 revision 和 SHA-256；不得把自创字段当上游布局协议。它仍作为原始提示词文本传给模型，不新增可执行结构或产品布局编辑器。

## 4. 每个新配方的正式产品执行

以下 P 用例对三个新配方**分别执行**。允许同一 Job 的证据覆盖相关行，但不能把一次执行记录成多次连续任务。

| ID | 级别/层 | 操作 | 通过条件 |
|---|---|---|---|
| P01 | P0/model | 通过正式宿主依次执行 T01–T03，MOSS 另执行 T04 | 真实成功 Attempt、独立 Job/资产、PNG 完整解码为 RGB 1024²、bytes/hash/RunManifest 一致，实际型号/能力名称不串用 |
| P02 | P0/质量 | 与 B01/B02/B03 同配方样图对照 | 参数/模板/尺寸/种子一致；没有黑图/空白/损坏或集成引入的系统性语义退化；记录审阅者和逐项文字/布局评语 |
| P03 | P0/model/native | 同一会话连续完成至少三次独立发送 | 没有旧状态或随机数串用，单活动约束成立，图片归属正确；可复用 P01 的三个真实 Job |
| P04 | P0/model | 宿主、监督与 worker 整进程树禁网执行 T01 | 正式图片提交，无配置补件或动态下载；可与 P01 的 T01 共用证据 |
| P05 | P0/model | 在真实加载取消，然后在真实采样取消并显式重试 | 旧 Attempt Cancelled、无新正式资产；资源回收后新 token/Attempt 使用原冻结种子成功 |
| P06 | P0/model | 在至少一个真实 GPU 采样步返回后强杀本次隔离宿主，重开同根并显式重试 | 旧 Interrupted，旧租约释放前拒绝新生成，清理后按原型号/配方重试成功 |
| P07 | P0/model/contracts | 空白/超 16 KiB/非法种子/非方形/多张/未知参数输入 | 在相应边界拒绝，原输入和先前有效默认值可恢复，不静默调整或替换模型 |
| P08 | P0/model | 按真实模板验证低于/恰好边界附近/超过 token 预算的输入 | Qwen 不沿用 512，MOSS 不沿用 2048；没有 truncation；实际数量和恢复编辑可核对 |
| P09 | P0/contracts/native | 观察对应 total 的最后一步、解码与候选未提交阶段 | Turbo=8、Qwen=40、MOSS=50；最后一步不能成为 100% 成功，CFG 分支不被当成额外去噪步 |
| P10 | P0/记录 | 核对请求、有效计划、PNG、RunManifest、任务/作品投影 | 模型/快照/runtime/recipe/精度/量化/采样/种子一致；原始用户输入不被有效参数覆盖 |
| P11 | P1/性能 | 同输入/种子至少三次独立进程重复，记录实际缓存条件 | 分别记录预检/加载/Job/采样可测时间和资源；没有驻留热池则不写“热模型性能” |

P02 不要求跨进程逐像素相同，也不承诺生成文字必然无错。文字或布局问题需判断是否已存在于同配方基线；基线已有的限制公开记录，产品新增的退化阻止通过。不能通过偷偷换 q4/q8、模板、分辨率、步数或种子消除差异后仍称同配方比较。无法做出判断时保留 blocked 并补证据，不能只填“看起来不错”。

P08 需要真正 tokenizer 的边界输入，其完整文本和实际计数在基线准备时保存为 fixture；字符数不是 token 数。P05/P06 不得在默认用户数据根执行，故障 fixture 不能代替这些真实模型事件。

## 6. 报告、性能与阶段结论

每个配方用配置指纹关联来源、包锁、实际输入、有效参数、真实输出和原生日常证据；报告分别输出 passed/failed/not_run/blocked。基线、fixture、设备探针、正式 real_execution 和 native_ui 分列，不能让新模型继承旧报告的 passed。

实施前G0先核对三个计划型号整批认证与归档、及本方案用户确认。进入本批后按G1–G5顺序完成所有 P0。新增三配方全通过并且前置四型号当前回归通过后才是整批完成；Qwen 两项通过只能作为阶段结果，不能关闭 MOSS 或归档全部 change。P1 的更多精度/重复性能可以未运行，但必须给原因。

性能记录至少包含入口/缓存条件、模型加载方式、Job 接收到资产提交时间，以及能准确取得的预检/编码/采样/解码分段；无法准确测得的分段为 null。资源区分 `/usr/bin/time -l` RSS、MLX 可观测峰值与 UI 宿主，不相互替代。不从上游其他芯片数字推导本机速度，不对不同提示词的耗时直接求“模型平均速度”。
